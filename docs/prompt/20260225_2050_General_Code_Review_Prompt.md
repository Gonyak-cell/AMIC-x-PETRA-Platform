````
## 리뷰 절차

### 0단계: 변경 범위 파악
- `git diff`와 `git diff --cached`로 실제 변경 내역을 확인
- 수정된 파일을 모두 `Read`로 전체 읽기 (변경된 줄만이 아닌 파일 전체)
- 변경된 파일이 import/호출하는 모듈과 의존 타입도 반드시 읽기
- 최초 계획 문서가 있으면 반드시 `Read`로 읽어서 계획된 기능 목록을 파악

---

### 1단계: 기존 코드와의 정합성 (Consistency)

변경된 코드가 기존 코드베이스의 패턴, 컨벤션, 구조와 일치하는지 검증.

#### [백엔드]
- **계층 구조**: 라우터→서비스→모델 3계층 분리 준수 여부 (라우터에 비즈니스 로직 혼입 금지)
- **네이밍 컨벤션**: 함수명 snake_case, 클래스명 PascalCase, 테이블명 snake_case 복수형 등 기존 패턴과 일치 여부
- **import 순서**: stdlib → third-party → local 순서 유지 여부
- **스키마 패턴**: Pydantic v2 `model_config = ConfigDict(from_attributes=True)` 사용 여부, `Create`/`Update`/`Response` 분리 패턴 준수 여부
- **에러 처리 패턴**: 기존 커스텀 예외 클래스(`AppError`, `NotFoundError` 등) 활용 여부, 새로운 예외 클래스 무분별 생성 여부
- **로깅 패턴**: `logging.getLogger(__name__)` 사용, 구조화된 JSON 로깅 일관성
- **의존성 주입**: `Depends()` 패턴 일관성, `get_current_user` 주입 방식 동일 여부
- **동일 모듈 내 유사 코드 비교**: 같은 디렉토리의 다른 파일(예: 다른 라우터)을 `Read`로 읽어서 패턴 비교

#### [프론트엔드]
- **훅 패턴**: `useQuery`/`useMutation` 사용 방식이 기존 훅들(`useDeals.ts`, `useTransactions.ts` 등)과 동일한지
- **컴포넌트 패턴**: Props 인터페이스 정의, `forwardRef` 사용, `cn()` 유틸리티 사용 등 기존 패턴 일치 여부
- **파일 구조**: `modules/{module}/pages/`, `hooks/`, `types/`, `components/` 구조 준수 여부
- **타입 정의 위치**: 모듈별 `types/` 폴더에 정의, 공유 타입은 `src/types/`에 정의 등 기존 규칙 준수
- **API 호출 패턴**: axios 인스턴스 사용, `withCredentials: true`, 에러 핸들링 방식 일관성
- **동일 모듈 내 유사 페이지 비교**: 같은 모듈의 다른 페이지를 `Read`로 읽어서 구조 비교

---

### 2단계: 코드 완성도 및 기능 구현 완전성 (Completeness)

변경된 코드가 의도한 기능을 완전히 구현했는지 검증.

#### [기능 완전성]
- **최초 계획 대비 누락 검증**: 계획 문서에 명시된 기능/엔드포인트/UI 요소가 모두 구현되었는지 항목별 대조
  - 계획 문서의 각 항목에 대해 ✅ 구현됨 / ❌ 누락 / ⚠️ 부분 구현 으로 체크리스트 작성
- **엔드포인트 완전성**: CRUD 중 누락된 메서드가 없는지 (예: Create는 있는데 Delete가 없는 경우)
- **에러 경로**: 정상 경로만 구현하고 에러/예외 경로 처리를 빠뜨리지 않았는지
- **엣지 케이스**: 빈 목록, null 값, 권한 없는 사용자, 존재하지 않는 리소스 등 경계 상황 처리 여부
- **유효성 검증**: 입력 데이터에 대한 검증이 충분한지 (필수 필드, 형식, 범위)

#### [통합 완전성]
- **라우터 등록**: 새 라우터가 `main.py`에 `include_router()`로 등록되었는지
- **프론트엔드 라우팅**: 새 페이지가 `App.tsx` 또는 모듈별 `Routes.tsx`에 등록되었는지
- **사이드바/내비게이션**: 새 페이지에 대한 메뉴 항목이 추가되었는지
- **타입 export**: 새 타입이 `index.ts` 배럴 파일에서 export되는지
- **마이그레이션**: DB 스키마 변경 시 Alembic 마이그레이션 파일이 존재하는지, `downgrade()` 구현 여부

#### [테스트 완전성]
- **새 기능에 대응하는 테스트 존재 여부**: 추가된 API 엔드포인트에 대한 테스트, 새 컴포넌트에 대한 테스트
- **기존 테스트 영향**: 변경으로 인해 기존 테스트가 깨질 수 있는지 분석
- **테스트 품질**: 실제 동작을 검증하는지 (구현 세부가 아닌 행동 테스트)

---

### 3단계: 코드 난이도/수준/깊이 (Quality & Depth)

코드의 기술적 품질과 엔지니어링 수준을 평가.

#### [설계 품질]
- **적절한 추상화 수준**: 과도한 추상화(불필요한 헬퍼/유틸리티 클래스) 또는 부족한 추상화(중복 코드) 여부
- **관심사 분리**: 한 함수/클래스가 너무 많은 책임을 지지 않는지 (SRP)
- **데이터 흐름 명확성**: 데이터가 어디서 오고 어디로 가는지 코드만 보고 추적 가능한지
- **상태 관리**: 불필요한 상태 사용 여부, 파생 가능한 값을 별도 상태로 관리하지 않는지

#### [구현 수준]
- **타입 시스템 활용도**: 제네릭, 유니온, 디스크리미네이티드 유니온 등 TypeScript 기능 적절 활용 여부 / Python 타입 힌트 완비 여부
- **비동기 처리**: async/await 올바른 사용, 불필요한 await 없는지, 병렬 가능한 작업의 동시 실행 여부
- **쿼리 최적화**: N+1 방지, 적절한 인덱싱, 불필요한 전체 조회 여부
- **메모리/성능**: 대용량 데이터 페이지네이션, 불필요한 전체 로딩 방지, 프론트엔드 불필요 리렌더링 방지

#### [코드 가독성]
- **함수/변수 네이밍**: 의미가 명확한지, 약어 남용 여부
- **함수 길이**: 한 함수가 50줄을 넘지 않는지 (넘으면 분리 권장)
- **주석 필요성**: 복잡한 비즈니스 로직에 대한 설명 주석이 있는지 (자명한 코드에 불필요한 주석이 없는지)

---

### 4단계: 안정성 (Stability & Safety)

프로덕션 환경에서 안정적으로 동작할 수 있는지 검증.

#### [보안]
- **하드코딩된 시크릿**: API 키, 비밀번호, 토큰이 코드에 포함되어 있지 않은지
- **인증/인가**: 모든 보호 엔드포인트에 `Depends(get_current_user)` 존재 여부, 권한 체크 누락 여부
- **입력 검증**: 사용자 입력이 Pydantic 또는 명시적 검증을 거치는지
- **SQL 인젝션**: 문자열 결합 대신 파라미터화된 쿼리 사용 여부
- **XSS**: `dangerouslySetInnerHTML` 사용 시 sanitize 여부
- **CORS**: 와일드카드(`*`) 미사용 확인

#### [에러 복원력]
- **예외 처리 범위**: try-catch/except 블록이 적절한 범위로 설정되었는지 (너무 넓거나 좁지 않은지)
- **실패 시 일관된 상태**: DB 트랜잭션에서 예외 발생 시 롤백이 보장되는지
- **외부 서비스 장애 대응**: 다른 백엔드 모듈 호출 실패 시 적절한 폴백/에러 반환 여부
- **타임아웃**: 외부 API/DB 호출에 적절한 타임아웃 설정 여부

#### [데이터 무결성]
- **DB 제약 조건**: NOT NULL, UNIQUE, FK 등 적절한 제약 조건 설정 여부
- **동시성**: 레이스 컨디션 가능성 (동시 업데이트, 중복 생성 등)
- **마이그레이션 안전성**: 마이그레이션이 기존 데이터를 손상시키지 않는지, 대용량 테이블 영향 여부

#### [모듈 간 계약]
- **BE Pydantic ↔ FE TypeScript 필드 일치**: 필드명, 타입, nullable 모두 일치하는지 (실제 양쪽 파일을 Read로 읽어서 비교)
- **엔드포인트 경로/메서드 일치**: 프론트엔드 API 호출 URL이 백엔드 라우터 경로와 정확히 매칭하는지
- **열거형(Enum) 값 동기화**: 백엔드 Enum 값과 프론트엔드 상수/타입이 일치하는지

### 5단계: 허위 리뷰 방지 검증 (Anti-False-Positive)

**모든 이슈를 보고하기 전에 반드시 아래 5개 항목을 각 이슈에 대해 검증.**
하나라도 실패하면 해당 이슈를 삭제하거나 신뢰도를 LOW로 하향.

- [ ] **SC-1 도달 가능성**: 이 코드가 실제로 실행되는 경로에 있는가? (죽은 코드, 주석 처리된 코드, 비활성 기능이 아닌지)
- [ ] **SC-2 부재 주장 검증**: "X가 없다"는 주장을 했다면, `Grep`으로 전체 코드베이스에서 부재를 확인했는가? (배럴 export, 별칭, 동적 import 포함)
- [ ] **SC-3 프레임워크 처리**: React, TanStack Query, FastAPI, SQLAlchemy 등 프레임워크가 이미 처리하는 부분을 지적하고 있지 않은가?
- [ ] **SC-4 의도된 패턴**: 기존 코드베이스에서 동일한 패턴이 사용되고 있지 않은가? (`Grep`으로 같은 패턴의 다른 사용처를 검색)
- [ ] **SC-5 수정 안전성**: 제안한 수정이 타입 에러, 런타임 에러, 다른 기능 파괴를 야기하지 않는가?

---

### 6단계: 최초 계획 대비 누락 분석 (Plan Compliance)

최초 계획 문서가 제공된 경우 반드시 수행.

- 계획 문서를 `Read`로 읽고, 명시된 기능/요구사항을 **전수 목록**으로 추출
- 각 항목에 대해 실제 코드에서 구현 여부를 확인하고 체크리스트 작성:

```
## 최초 계획 대비 구현 검증

| # | 계획된 항목 | 구현 상태 | 검증 근거 (파일:라인) |
|---|-----------|---------|---------------------|
| 1 | {항목1}   | ✅/❌/⚠️ | {파일:라인 또는 미발견} |
| 2 | {항목2}   | ✅/❌/⚠️ | {파일:라인 또는 미발견} |
| ...| ...      | ...     | ...                 |
```

- ✅ 완전 구현: 계획대로 구현 확인됨
- ⚠️ 부분 구현: 일부만 구현되었거나 계획과 다르게 구현됨 (차이점 설명)
- ❌ 누락: 구현되지 않음 (누락 사유 분석)

---

### 출력 형식

#### 리뷰 요약
- 총 이슈 수: N개 (Critical: X, Major: Y, Moderate: Z, Minor: W)
- 계획 대비 구현율: X/Y 항목 (Z%)
- 전체 평가: {한 줄 요약}

#### 이슈 목록 (심각도 내림차순)

각 이슈:
```
### [{심각도}] {이슈 제목}
- **위치**: `파일경로:라인번호`
- **카테고리**: 정합성 / 완전성 / 품질 / 안정성
- **신뢰도**: HIGH / MEDIUM / LOW
- **셀프 체크**: SC-1(✓) SC-2(✓) SC-3(✓) SC-4(✓) SC-5(✓)
- **근거**: (실제 Read로 읽은 코드 스니펫)
- **설명**: 무엇이 문제인지
- **영향**: 문제가 발생하면 어떤 일이 일어나는지
- **수정 제안**: 구체적인 코드 변경 방향
```

#### 계획 대비 누락 분석 표 (6단계 결과)

## 핵심 원칙
- **추측 금지**: "아마 ~일 것이다"로 시작하는 이슈 금지. 모든 주장은 실제 Read/Grep 확인 기반.
- **증거 첨부 필수**: Read 출력에서 가져온 실제 코드 스니펫을 근거로 제시. 기억이나 재구성된 코드 사용 금지.
- **허위 양성 방지**: 셀프 체크 5항목 중 하나라도 실패하면 이슈 삭제 또는 신뢰도 LOW로 명시.
- **파일 전체 맥락**: 변경된 줄만 보지 않고, 파일 전체와 관련 파일을 읽어서 맥락을 파악.
- **비교 기반 정합성**: 기존 코드베이스의 유사 파일을 반드시 읽어서 패턴 일치 여부를 비교 검증.
````

## 상황별 축약 버전

### 1. 가장 간편한 버전 (git diff 기반 자동)
```
`git diff`와 `git diff --cached`로 현재 변경사항을 확인하고, 변경된 모든 파일에 대해 전체 코드 리뷰를 수행해줘.
최초 계획 문서: {경로}
[위 전체 리뷰 지침 적용]
```

### 2. 백엔드만 변경
```
최근 수정한 백엔드 코드 리뷰. 변경 파일: {파일들}
최초 계획: {경로}
리뷰 항목: 정합성(백엔드), 완전성, 품질, 안정성(보안+DB), 허위리뷰 방지, 계획 대비 누락
```

### 3. 프론트엔드만 변경
