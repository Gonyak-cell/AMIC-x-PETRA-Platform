# FDD vs LDD 멀티 LLM 아키텍처 비교

> 생성: 2026-02-25 22:04

---

## 1. 멀티 LLM이 필요한가?

결론: **"반드시 멀티 LLM이어야 하는 건 아니지만, 특정 구간에서는 확실히 효과가 있다."**

### 멀티 LLM이 효과적인 구간

1. **수치 검증 (Cross-verification)** — LLM A가 추출하면 LLM B가 독립 검증. 단일 LLM은 자기 출력을 맹신하는 경향.
2. **관점 다양화 (Perspective diversity)** — "리스크 관점"과 "기회 관점"을 다른 모델이 각각 분석. 단일 모델은 프롬프트로 관점을 바꿔도 비슷한 톤으로 수렴.
3. **언어/형식 특화** — 한국 규제 분석은 한국어 특화 모델, 영문 레포트는 영어 네이티브 모델, 수치 테이블 파싱은 코드 생성 특화 모델.

### 멀티 LLM이 불필요한 구간

1. **내러티브 생성** — 단일 고성능 모델 + 좋은 프롬프트가 더 효율적. 여러 모델 병합 시 톤 불일치.
2. **구조화된 추출** — `LLM 1개 + deterministic validation`이 비용 대비 효과적.
3. **템플릿 슬롯 채우기** — 모델 하나면 충분.

## 2. FDD 멀티 LLM 파이프라인

### 전체 파이프라인

```
[Stage 1] 데이터 파싱 ── 단일 LLM + 코드
│  Excel/PDF → 숫자 추출은 코드(pandas, openpyxl)
│  비정형 주석/각주 해석만 LLM 1개 (Sonnet, 비용 효율)
│
[Stage 2] 분석 엔진 ── 단일 LLM, 섹션별 병렬
│  QoE 조정항목 분류, NWC 분류, Net Debt 분류
│  각 섹션 독립이므로 병렬 호출 가능
│  추천: Opus 또는 GPT-4o (분석 정확도 우선)
│
[Stage 3] 수치 교차검증 ── 멀티 LLM ★핵심★
│
│  ┌─ Writer (GPT-4o) ──────────┐  ┌─ Reviewer (Claude) ─────────┐
│  │ "이 조정이 타당한가?"       │  │ 독립적으로 동일 GL 분류      │
│  │ "금액 산출 근거는?"        │  │ "이 조정에 빠진 것은?"       │
│  └────────────┬───────────────┘  └────────────┬────────────────┘
│               └───────────┬───────────────────┘
│                           ▼
│                   비교 로직 (코드)
│                           │
│            ┌──────────────┼──────────────┐
│            ▼              ▼              ▼
│         일치항목       불일치항목       누락항목
│        자동 승인     사람 검토 필요    추가 분석
│
│  불일치 판정 기준:
│    금액 5%+ 차이 → MODERATE
│    금액 15%+ 차이 → MAJOR
│    분류 불일치 (NON_RECURRING ↔ OPERATING) → MAJOR
│    한쪽만 식별 → CRITICAL
│
│  자동 해결 규칙:
│    한쪽 UNCLEAR + 다른 쪽 명확 → 명확한 쪽 채택
│    한쪽이 원본 금액과 정확히 일치 → 일치하는 쪽 채택
│    confidence 차이 0.4+ → 높은 쪽 채택
│
[Stage 4] 레포트 생성 ── 단일 LLM
│  Executive Summary, 각 섹션 내러티브
│  추천: Opus (톤 일관성, 여러 모델로 쓰면 톤 불일치)
│
[Stage 5] 최종 QA ── 멀티 LLM ★
│  분석/서술에 안 쓴 모델 (Gemini Flash)로 팩트체크
│  ├─ 수치 인용이 원본과 일치하는가?
│  ├─ 섹션 간 크로스레퍼런스 일관성
│  ├─ 결론이 분석과 모순되지 않는가?
│  └─ 누락된 중요 발견사항
│
│  점수 3 미만 → 경고 포함하여 반환
```

### FDD 모델 배정 요약

| Stage | 모델 수 | 추천 조합 | 이유 |
|-------|---------|----------|------|
| 1. 파싱 | 1 | Sonnet | 비용 효율 |
| 2. 분석 | 1 | Opus/GPT-4o | 분석 정확도 |
| 3. 수치 검증 | **2** | **GPT-4o + Claude** | 교차검증 핵심 |
| 4. 레포트 | 1 | Opus | 톤 일관성 |
| 5. QA | **2** | **Gemini Flash** | 팩트체크 (비용 효율) |

비용: 기존 $5.00/딜 → $6.80/딜 (+36%)

## 3. LDD 멀티 LLM 파이프라인

### 전체 파이프라인

```
[Stage 1] 문서 수집/분류 ── 단일 LLM + 코드
│  VDR 문서(PDF/Word/스캔) → OCR + 파일 분류
│  문서 유형 판별: SHA, 정관, 등기부, 인허가, 소송 등
│  추천: Sonnet/Haiku (분류 작업, 비용 효율)
│
[Stage 2] 조항 추출/구조화 ── 단일 LLM
│  문서 유형별 전문 프롬프트로 구조화된 조항 추출
│  출력: {clause_id, type, article, summary, parties,
│         trigger_conditions, consequences, raw_text}
│  추천: Opus (복잡한 법률 문서 이해력)
│
[Stage 3] 리스크 분석 ── 멀티 LLM ★핵심★
│
│  ┌─ LLM A (매수인 관점) ──────┐  ┌─ LLM B (독립 리스크 평가) ──┐
│  │ "매수인 입장에서 이 조항의   │  │ "이 조항이 거래 완결에       │
│  │  리스크를 평가하라"         │  │  미치는 영향을 독립 평가하라" │
│  │                            │  │                             │
│  │ SHA-001: risk=HIGH         │  │ SHA-001: risk=CRITICAL      │
│  │ "CoC 트리거 가능성 있으나   │  │ "사전 동의 미확보 시         │
│  │  면제 협상 여지 있음"       │  │  계약 해지 → 거래 무산"      │
│  └────────────┬───────────────┘  └────────────┬────────────────┘
│               └───────────┬───────────────────┘
│                           ▼
│                   비교 로직 (코드)
│                           │
│           ┌───────────────┼───────────────┐
│           ▼               ▼               ▼
│        일치 (LOW)     등급 불일치      일치 (HIGH+)
│        자동 포함      변호사 검토       우선 보고
│
│  불일치 처리:
│    gap=0 → 해당 등급으로 자동 확정
│    gap=1 → 높은 쪽 채택 + 양측 근거 병기
│    gap≥2 → 변호사 필수 검토
│
[Stage 4] 누락 탐지 ── 멀티 LLM ★가장 중요★
│
│  ┌─ LLM A (체크리스트 기반) ──┐  ┌─ LLM B (자유 탐색 기반) ────┐
│  │ "M&A 표준 LDD 체크리스트    │  │ "이 거래의 특수성을 고려해    │
│  │  대비 누락된 검토 항목"     │  │  추가로 확인할 사항은?"      │
│  │                            │  │                             │
│  │ □ 환경 실사 미수행          │  │ □ 대상회사가 식품업 →        │
│  │ □ 노동법 준수 확인 없음     │  │   식약처 인허가 이전 가능성   │
│  │ □ 지적재산권 실사 누락      │  │ □ 최근 법인세법 개정 →       │
│  │ □ 보험 검토 없음            │  │   이연법인세 재평가 필요      │
│  └────────────┬───────────────┘  └────────────┬────────────────┘
│               └───────────┬───────────────────┘
│                           ▼
│                   합집합 = 최종 누락 목록
│                   (중복 제거, 우선순위 정렬)
│
│  핵심: 체크리스트 기반 = "표준 항목" 커버
│        자유 탐색 기반 = "거래 특수 항목" 커버
│        합집합이 단일 모델보다 커버리지 확실히 높음
│
[Stage 5] 관할권 교차 분석 ── 멀티 LLM (크로스보더 시만)
│
│  ┌─ LLM A (한국법 전문) ──────┐  ┌─ LLM B (영미법 전문) ───────┐
│  │ 상법, 공정거래법, 외투법     │  │ SPA R&W, Indemnity          │
│  │ 한국어 법률 용어 정확도      │  │ 영어 법률 용어 정확도        │
│  └────────────┬───────────────┘  └────────────┬────────────────┘
│               └───────────┬───────────────────┘
│               교차점: 양 관할권 모두 영향 받는 조항
│               충돌점: 관할권 간 상충하는 요구사항
│
[Stage 6] 레포트 생성 ── 단일 LLM
│  통합 LDD 레포트 (Corporate, Contracts, Litigation,
│  Regulatory, Real Estate, Employment, IP 등)
│  추천: Opus (법률 톤 일관성)
│
[Stage 7] 최종 QA ── 멀티 LLM
│  ├─ 인용된 조항 번호 ↔ 원본 일치
│  ├─ 리스크 등급 ↔ 권고사항 논리 일관성
│  ├─ 누락된 표준 검토 항목
│  └─ 법률 용어 정확성
```

### LDD 모델 배정 요약

| Stage | 모델 수 | 추천 조합 | 이유 |
|-------|---------|----------|------|
| 1. 문서 분류 | 1 | Sonnet | 비용 효율 |
| 2. 조항 추출 | 1 | Opus | 법률 문서 이해 |
| 3. 리스크 분석 | **2** | **Opus + GPT-4o** | 관점 다양화 |
| 4. 누락 탐지 | **2** | **Opus + GPT-4o** | 커버리지 극대화 |
| 5. 관할권 교차 | **2** | **언어별 특화** | 해당 시만 |
| 6. 레포트 | 1 | Opus | 톤 일관성 |
| 7. QA | **2** | **Gemini** | 팩트체크 |

비용: 기존 대비 ~2.2배

## 4. FDD vs LDD 종합 비교

| 항목 | FDD | LDD |
|------|-----|-----|
| 멀티 LLM 적용 Stage | 2곳 (수치 검증, QA) | **4곳** (리스크, 누락, 관할권, QA) |
| 가장 ROI 높은 구간 | 수치 교차검증 | **누락 탐지** |
| 불일치 비교 방식 | 금액 % 차이 + 분류 일치 | 리스크 등급 gap + 합집합 |
| 자동 해결 가능 비율 | 높음 (수치 대조 가능) | 낮음 (해석 영역) |
| 사람 개입 포인트 | 불일치 수치 검토 | 불일치 리스크 + 누락 항목 |
| 총 비용 배수 | ~1.6x | ~2.2x |
| 환각 위험도 | 중간 (수치 대조 가능) | **높음** (조항 인용 검증 필수) |

## 5. LDD에서 멀티 LLM ROI가 FDD보다 높은 이유

### 5.1. 오류의 성격 차이

```
FDD 오류 = "숫자가 틀림"
  → 원본 데이터와 대조하면 코드로 잡을 수 있음
  → 멀티 LLM 없이도 deterministic 검증 가능한 부분이 많음

LDD 오류 = "해석이 다름" 또는 "빠뜨림"
  → 코드로 잡을 수 없음
  → 다른 모델의 "다른 시각"이 유일한 검증 수단
```

### 5.2. 법률은 "해석"이 핵심 — 단일 모델의 편향이 위험

FDD에서 "이 항목은 NON_RECURRING인가?"는 상대적으로 객관적. 소송비용 10억은 대부분 비경상.

LDD에서 "이 Change of Control 조항이 트리거되는가?"는 관점에 따라 달라짐:

```
같은 조항에 대해:

모델 A: "리스크 LOW — 지분 50% 이상 변동이 조건인데,
         이번 거래는 40% 인수이므로 트리거 안 됨"

모델 B: "리스크 HIGH — 40% 인수 후 경영권 변동이 발생하면
         실질적 지배력 변경으로 해석될 수 있음.
         계약서 '실질적 지배력' 조항 확인 필요"
```

모델 A만 쓰면 리스크를 놓침. 모델 B만 쓰면 과잉 경고. 양쪽 의견이 모두 있어야 변호사가 올바르게 판단할 수 있음.

### 5.3. 누락 리스크의 치명도 차이

```
FDD에서 조정항목 1개 빠짐:
  → EBITDA 2% 오차
  → 밸류에이션 조정으로 보완 가능
  → 딜이 깨지진 않음

LDD에서 조항 1개 빠짐:
  → Change of Control 미확인 → 거래 후 핵심 계약 해지
  → 인허가 이전 불가 → 사업 영위 자체 불가
  → 소송 미파악 → 수백억 우발부채 발생
  → 딜이 깨지거나, 인수 후 대규모 손실
```

### 5.4. 단일 모델 대비 멀티 모델의 리스크 탐지율

| 리스크 유형 | 단일 모델 | 멀티 모델 (합집합) |
|------------|----------|------------------|
| 명시적 리스크 (계약서에 분명히 적힌 것) | ~95% | ~98% |
| 암묵적 리스크 (해석이 필요한 것) | ~60% | **~80%** |
| 교차 조항 리스크 (A조항+B조항 결합) | ~40% | **~65%** |

암묵적/교차 리스크에서 차이가 크게 벌어짐.

### 5.5. 누락 탐지에서 두 접근법의 보완 관계

```
체크리스트 기반만:        자유 탐색 기반만:        합집합:
□ 환경 실사               □ 식품업→식약처 인허가    □ 환경 실사
□ 노동법 준수             □ 법인세법 개정 영향      □ 노동법 준수
□ IP 실사                □ 합작법인 소수주주 권리    □ IP 실사
□ 보험 검토                                       □ 보험 검토
                                                  □ 식약처 인허가 ★
                                                  □ 법인세법 영향 ★
                                                  □ 소수주주 권리 ★
```

★ = 단일 모델로는 놓칠 수 있는 거래 특수 항목

### 5.6. 관할권 교차 분석 — LDD에만 있는 멀티 LLM 구간

크로스보더 M&A에서:

```
한국법 분석 LLM:                    영미법 분석 LLM:
"공정거래법상 기업결합신고            "SPA의 Representations &
 30일 전 사전신고 의무"               Warranties 범위가 한국
                                    공시 의무와 상충"

→ 교차점: 양쪽 모두 영향 받는 조항 자동 식별
→ 충돌점: "한국법상 의무 vs 영미법상 면책" 자동 탐지
```

FDD에는 이 구간 자체가 없음. 숫자는 관할권에 따라 바뀌지 않기 때문.

### 5.7. ROI 정량 비교

| 지표 | FDD | LDD |
|------|-----|-----|
| 멀티 LLM 적용 구간 | 2곳 | **4곳** |
| 교차검증 비용 증가 | +36% (~$1.80) | +120% (~$4.00) |
| 코드로 대체 가능한 검증 비율 | ~60% | **~15%** |
| 단일 모델 대비 오류 감소 | ~15% | **~35%** |
| 오류 1건당 잠재 손실 | 억 단위 | **수십억~거래 무산** |
| **비용 대비 효과 (ROI)** | **중간** | **높음** |

핵심: LDD는 코드로 검증할 수 없는 영역이 85%이므로, 멀티 LLM이 유일한 자동화 검증 수단. FDD는 코드 검증으로 상당 부분 커버되므로 멀티 LLM의 추가 가치가 상대적으로 작음.

---

## 6. 한 줄 요약

- **FDD**: "숫자 틀림 방지"에 멀티 LLM → nice to have
- **LDD**: "빠뜨림 방지"에 멀티 LLM → **must have**
- FDD 멀티 LLM: 있으면 좋다 (코드 검증으로 상당 부분 대체 가능)
- LDD 멀티 LLM: 없으면 위험하다 (해석 다양성이 유일한 검증 수단, 누락 1건의 비용이 교차검증 비용의 수천 배)
