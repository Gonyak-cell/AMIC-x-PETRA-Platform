## 1. 개요

`통합_플랫폼_구현_계획서.md`를 기반으로 3개 백엔드의 실제 Pydantic 스키마를 프론트엔드 TypeScript 타입과 **필드 단위**로 대조하였다. 결과, 계획서 원안(5건)보다 **20건 이상의 불일치**가 확인되었다.

### 핵심 발견사항

| # | 발견 | 상세 |
|---|------|------|
| 1 | Phase A (IM 빌드 복구) 이미 완료 | `DocumentStatusBadge.tsx`, `ImErrorBoundary.tsx`, `useCompanies.ts` 3개 파일 모두 존재 |
| 2 | KIIS 타입 불일치 20건+ | 필드명 10건 + 타입(number→string) 9건 + 누락 필드 15건+ |
| 3 | KIIS 훅 응답 구조 불일치 7건 | 백엔드 래퍼(`{fund, managers}`, `{items}`) → 프론트 flat 배열 |
| 4 | FundManager 추가 불일치 | `name` → `manager_name`, `certifications: string[]` → `string` |
| 5 | 유틸리티 호환성 확보 | `formatAmount`, `formatPercent` 등이 이미 `number \| string` 모두 지원 |
| 6 | IM 모듈 99% 일치 | 타입 보완 거의 불필요 |

### Money Rules 결정

Pydantic v2는 `Decimal` 필드를 JSON 응답에서 **string으로 직렬화**한다 (`model_dump(mode='json')`). 따라서 모든 금액/비율 필드는 프론트엔드에서 `string | null`로 정의해야 한다.

`src/lib/format.ts`의 `formatAmount`, `formatPercent`, `formatCompact` 함수는 이미 `number | string` 입력을 모두 처리하므로, **유틸리티 수정 없이** 타입만 변경하면 된다.

- **스키마**: 12+ Pydantic 스키마
- **인증**: JWT RS256 (RS256 키 페어 또는 HS256 폴백)

## 4. 구현 계획

### Phase 1: KIIS 타입 백엔드 정합성 교정 (최우선)

KIIS 모듈의 4개 타입 파일을 백엔드 Pydantic 스키마와 1:1 매칭되도록 재작성한다.

| 작업 | 파일 | 주요 변경 |
|---|---|---|
| 1-A | `src/modules/kiis/types/fund.ts` | 필드명 2건 + 타입 3건 + 구조 변경 + 매니저 필드 수정 |
| 1-B | `src/modules/kiis/types/reit.ts` | 필드명 4건 + 타입 2건 + 누락 15건 + 구조 변경 |
| 1-C | `src/modules/kiis/types/deal.ts` | 필드명 3건 + 타입 4건 + 래퍼 4종 추가 |
| 1-D | `src/modules/kiis/types/sanction.ts` | 필드명 5건 + 누락 5건 |

### Phase 2: KIIS 훅 응답 구조 수정

모든 KIIS 훅에서 백엔드 래퍼 응답을 처리한다. **훅 내부에서 `.items` 또는 래퍼 필드를 추출**하여 페이지에 깔끔한 데이터를 전달한다.

| 파일 | 수정 훅 | 변경 방법 |
|---|---|---|
| `src/modules/kiis/hooks/useFunds.ts` | `useFundDetail` | 반환 타입을 `FundDetailResponse`로, 페이지에서 `.fund`, `.managers` 접근 |
| `src/modules/kiis/hooks/useReits.ts` | `useReitDetail` | 반환 타입을 `ReitDetailResponse`로, 페이지에서 `.reits`, `.assets` 접근 |
| `src/modules/kiis/hooks/useDeals.ts` | 4개 모두 | queryFn에서 `data.items` 추출하여 배열만 반환 |
| `src/modules/kiis/hooks/useSanctions.ts` | `useClassifiedSanctions` | queryFn에서 `data.items` 추출 |

### Phase 3: KIIS 페이지 연쇄 수정

타입과 훅 변경에 따라 페이지/컴포넌트 코드를 수정한다.

| 파일 | 수정 내용 |
|---|---|
| `kiis/pages/FundListPage.tsx` | `mgmt_fee_rate` 컬럼 제거 (목록 응답에 없는 필드) |
| `kiis/pages/FundDetailPage.tsx` | `data.fund` 접근, `management_fee_rate`, `row.manager_name`, `certifications` 단일 문자열 |
| `kiis/pages/ReitListPage.tsx` | `row.reits_name`, 총자산/부동산비율 추가 표시 |
| `kiis/pages/ReitDetailPage.tsx` | `data.reits` 접근, `reits_name`/`reits_type`, `asset_value`/`asset_ratio`, **KPI 카드 추가** (총자산, 배당수익률, 부동산비율, 상장여부) |
| `kiis/pages/DealSourcingPage.tsx` | `stage` (← `round_stage`), `keyField` 수정 |

| `kiis/pages/CompanyDetailPage.tsx` | 제재 필드명 수정 |
| `kiis/components/DealTrendChart.tsx` | `d.deal_count` (← `d.count`) |

### Phase 4: IM 타입 보완 (경미)

IM 모듈은 백엔드와 99% 일치하므로 수정 불필요.

- `Document` 타입: 백엔드 `DocumentResponse`와 완전 일치 ✅
- `Company` 타입: 백엔드 `CompanyResponse`와 완전 일치 ✅
- `ImTemplate` 타입: 백엔드에 `/templates` 엔드포인트 없음 → 하드코딩 유지 ✅

### Phase 5: 크로스 모듈 연동

| 작업 | 파일 | 구현 |

## 7. 작업 순서 및 의존관계

```
Phase 1 (KIIS 타입 교정)  ←── 최우선, 모든 것의 기반
     ↓
Phase 2 (KIIS 훅 수정)    ←── Phase 1과 함께 수행
     ↓
Phase 3 (KIIS 페이지 수정) ←── Phase 1-2 완료 후 연쇄 수정
     ↓
Phase 4 (IM 보완)          ←── 거의 불필요 (확인만)
     ↓
Phase 5 (크로스 모듈)      ←── Phase 3 이후 진행
```

- **Phase 1 + 2**는 밀접하게 연관 — 타입 파일별로 (타입 수정 → 훅 수정) 순서로 진행
- **Phase 3**은 Phase 1-2 완료 후 TypeScript 컴파일 에러를 따라가며 수정
- **Phase 5**는 독립적이나 Phase 3 이후가 안전

| KIIS 리츠 상세 | `/kiis/reits/{code}` | 상세 + KPI 카드 + 자산 테이블 |
| KIIS 딜 소싱 | `/kiis/deals` | 트렌드/섹터/스테이지 탭 |
| KIIS 제재 | `/kiis/sanctions` | 목록 + 상세 |
| KIIS → IM 연동 | `/kiis/companies/{code}` | "IM 생성" 버튼 → `/im/new?corpCode=...` |
| IM 자동 입력 | `/im/new?corpCode=00126380` | 법인코드 자동 입력 확인 |
| FDD 기존 기능 | `/fdd/deals` | 기능 유지 확인 (regression 없음) |
| 모듈 전환 | ModuleSwitcher | FDD/KIIS/IM 전환 정상 |
