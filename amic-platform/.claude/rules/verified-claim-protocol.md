# Verified Claim Protocol (VCP)

## 적용 범위

이 프로토콜은 **코드 리뷰 활동을 수행하는 모든 에이전트**에 적용되는 필수 규칙입니다.
코드 리뷰 시 이슈를 보고하기 전에 반드시 아래 6단계를 거쳐야 합니다.

---

## 6단계 검증 프로토콜 (3.5단계: Self-Challenge 포함)

잠재적 이슈를 감지할 때마다, 보고하기 전에 아래 단계를 **반드시** 수행합니다:

### 1단계 — 위치 확인 (Glob)

- 참조할 파일이 실제로 존재하는지 Glob으로 확인
- 파일 경로가 정확한지 검증 (오타, 이동, 삭제 여부)

### 2단계 — 코드 읽기 (Read)

- Read 도구로 해당 파일의 관련 영역을 직접 읽기
- **메모리나 추론에 의존하지 않고** 실제 코드를 확인
- 라인 번호가 정확한지 대조

### 3단계 — 주장 검증

주장 유형별 검증 방법:

| 주장 유형 | 검증 방법 |
|----------|----------|
| "X가 없다" | Grep으로 전체 코드베이스 검색하여 부재 확인 |
| "X가 잘못 사용됨" | 주변 컨텍스트(import, 호출부, 설정 파일) 확인 |
| "X여야 한다" | FDD 레퍼런스 구현과 비교 확인 |
| "X가 취약하다" | 실제 공격 경로가 존재하는지 코드 흐름 추적 |
| "X가 중복이다" | 두 위치 모두 Read하여 실제 중복 확인 |

### 3.5단계 — 자기 반론 (Self-Challenge)

> **언제 실행하는가**: 3단계 검증을 통과하여 이슈 초안이 완성된 직후.
> 이슈를 발견한 에이전트가 스스로 **적대적 재검토자** 역할을 맡아 동일 코드를 다시 검토한다.
> Claude Code Security의 핵심 기법 — 발견 후 재검토로 허위 양성을 사전에 제거한다.

Self-Challenge는 이슈를 **기각(REJECT)**하거나 **신뢰도를 하향 조정**하기 위해 수행한다.
모든 항목에 답하고 판정을 기재한다.

| 항목 | 질문 | 판정 기준 |
|------|------|---------|
| **SC-1** 실행 경로 | 이 코드는 실제로 도달 가능한 경로인가? (dead code, disabled 상태, feature flag 확인) | ✓ 실행 가능 / ✗ REJECT / △ 조건부→MEDIUM |
| **SC-2** 의존성 부재 | "X가 없다"고 주장했다면 Grep으로 다시 확인했는가? barrel export 등 우회 경로는 없는가? | ✓ 실제로 없음 / ✗ REJECT / △ 불확실→LOW |
| **SC-3** 라이브러리 동작 | React, Tanstack Query, Zustand 등이 내부적으로 처리하는 기능을 "누락"으로 오판하지 않았는가? | ✓ 실제 이슈 / ✗ REJECT / △ 불확실→MEDIUM |
| **SC-4** 백엔드 계약 | 스키마 불일치를 주장했다면 실제로 백엔드 코드를 읽었는가? 미확인 시 신뢰도는 MEDIUM 이하여야 한다. | ✓ 백엔드 확인 / ✗ REJECT(가정만) / △ 미확인→MEDIUM |
| **SC-5** 의도된 패턴 | 코드베이스 전체에서 동일 패턴이 사용되는가? Grep으로 확인했는가? 일관된 패턴은 이슈가 아닐 수 있다. | ✓ 패턴 불일치 / ✗ REJECT(의도된 패턴) / △ 불명확→MEDIUM |
| **SC-6** 수정안 안전성 | 제안한 수정안이 타입 에러, 런타임 오류, 인터페이스 계약 위반을 유발하지 않는가? | ✓ 수정안 안전 / 수정안 재작성 후 재검토 |

#### Self-Challenge 판정 결과

**PASS (이슈 유지)**:
- SC-1~SC-5 모두 ✓ → 신뢰도 변동 없음
- 1개 이상 △ → 신뢰도 MEDIUM으로 하향 (이미 MEDIUM이면 유지)
- 2개 이상 △ → 신뢰도 LOW로 하향

**REJECT (이슈 기각)**:
- SC-1~SC-5 중 하나라도 ✗ 판정 → 해당 이슈를 보고하지 않음
- 거부 카테고리에 기재: `반증됨` / `오판` / `범위 외` / `Self-Challenge 기각` 중 선택

---

### 4단계 — 증거 첨부

- Read 도구에서 가져온 **실제 코드 스니펫**을 포함
- 메모리에서 재구성한 코드가 아닌, 도구 실행 결과 그대로 인용
- 파일 경로와 라인 번호를 정확히 기재

### 5단계 — 신뢰도 점수

각 이슈에 아래 기준으로 신뢰도를 부여:

| 점수 | 기준 | 설명 |
|------|------|------|
| **HIGH** (90%+) | Read/Grep 증거로 직접 확인 | 코드가 명확히 문제임을 증명 |
| **MEDIUM** (60-89%) | 증거는 강하나 불확실 요소 존재 | 런타임 동작, 백엔드 응답 등 미확인 |
| **LOW** (<60%) | 정황 증거만 존재 | 수동 검증 필요, 구조적 우려 |

---

## 거부 규칙 (CRITICAL)

> **3단계 또는 3.5단계(Self-Challenge)에서 가설이 반증되면, 해당 이슈를 보고하지 않는다.**
>
> 이것은 나중에 교정할 허위 양성이 아니라, 검증에 실패한 가설이다.
> 거부된 가설의 수는 리포트 말미에 투명하게 기록한다.
>
> - **3단계 거부**: 주장 검증에서 증거 반증 (예: "X가 없다" → Grep으로 발견)
> - **3.5단계 거부**: Self-Challenge에서 SC-1~SC-5 중 하나라도 ✗ 판정

---

## 금지 패턴

아래 패턴은 이 프로토콜을 위반하는 것으로 간주합니다:

1. **추측성 표현**: "~인 것 같다", "아마 ~일 것이다", "probably", "seems like"
2. **미확인 라인 번호**: Read 없이 라인 번호를 기재
3. **메모리 기반 코드 인용**: Read 결과가 아닌 기억에 의존한 코드 스니펫
4. **단일 파일 일반화**: 한 파일에서 확인한 패턴을 다른 파일에 검증 없이 일반화
5. **부재 미검증**: "X가 없다"를 Grep 없이 주장
6. **이전 세션 수치 재사용**: 파일 수, 이슈 수 등을 재카운트 없이 인용

## 표준 출력 형식

각 이슈는 아래 형식으로 보고합니다:

```
### [{SEVERITY_INITIAL}-{CATEGORY_INITIAL}{NUMBER}] {제목} — [{심각도}/{신뢰도}] — Priority: {P0/P1/P2/P3}

> 신뢰도 하향 시: `[Critical/MEDIUM ⚠️]` / `[Major/LOW ⚠️⚠️]` — 하향 이유를 추론 근거에 기재

- **파일**: {경로}:{라인}
- **에이전트**: {발견한 에이전트명}
- **교차 검증**: {Yes/No} {교차 검증 에이전트명}
- **우선순위**: {P0/P1/P2/P3} (점수: {계산된 점수})
  - 심각도 가중치: {100/70/40/20}
  - 신뢰도 가중치: {1.0/0.6/0.3}
  - 보너스: {+10 교차 검증} {+15 review-verifier 확인}
  - {신뢰도가 MEDIUM/LOW인 경우 하향 설명 추가}
- **검증 추적** (VCP 각 단계 실행 증거):
  1. ✓ Glob: `{pattern}` → {N}개 파일 발견
  2. ✓ Read: `{file}:{line-range}` → 코드 확인 완료
  3. ✓ Grep: `"{search-pattern}"` → {N}개 매칭 발견 (또는 "부재 확인")
  4. ✓ Context: `{related-files}` 확인 (import, 호출부, 설정 등)
  5. ✓ Self-Challenge: SC-1({✓/✗/△}) SC-2({✓/✗/△}) SC-3({✓/✗/△}) SC-4({✓/✗/△}) SC-5({✓/✗/△}) SC-6({✓}) → PASS / {신뢰도 조정 이유}
- **추론 근거**:
  - **심각도 {심각도}인 이유**: {정당화 — 왜 이 심각도인지 설명}
  - **신뢰도 {신뢰도}인 이유**: {정당화 — 증거 강도, 불확실 요소 설명}
- **증거**:
  ```{lang}
  {Read 도구에서 가져온 실제 코드}
  ```
- **이슈**: {구체적 설명}
- **영향**: {어떤 문제가 발생하는지}
- **수정안**:
  ```{lang}
  {제안하는 코드 변경}
  ```
```

심각도 기호:
- `C` = Critical (보안/데이터 무결성)
- `M` = Major (안정성/정확성)
- `m` = Moderate (코드 품질)
- `L` = Minor (개선 가능)

카테고리 기호 (에이전트별):
- `R` = code-reviewer (패턴/상태/UX)
- `T` = type-checker (타입 안전성)
- `A` = api-auditor (FE-BE 통합)
- `S` = security-auditor (보안)
- `Q` = test-auditor (테스트 품질)
- `X` = a11y-auditor (접근성)
- `P` = perf-auditor (성능)
- `I` = infra-auditor (인프라)

### 우선순위 계산 공식

**기본 공식**:
```
우선순위 점수 = (심각도 가중치 × 신뢰도 가중치) + 보너스
```

**심각도 가중치**:
- Critical: 100
- Major: 70
- Moderate: 40
- Minor: 20

**신뢰도 가중치**:
- HIGH (90%+): 1.0
- MEDIUM (60-89%): 0.6 (40% 하향)
- LOW (<60%): 0.3 (70% 하향)

**보너스**:
- 교차 검증 (2+ 에이전트 동일 이슈 발견): +10
- review-verifier 확인: +15

**우선순위 등급**:
- **P0** (90+): 즉시 수정 (보안/데이터 무결성)
- **P1** (60-89): 스프린트 우선 (안정성/정확성)
- **P2** (30-59): 개선 권장 (코드 품질)
- **P3** (<30): 저우선 (개선 가능)

**예시**:
1. Critical + HIGH 신뢰도 = 100 × 1.0 = 100 → **P0**
2. Critical + MEDIUM 신뢰도 = 100 × 0.6 = 60 → **P1** (P0 아님!)
3. Major + HIGH 신뢰도 + 교차 검증 = 70 × 1.0 + 10 = 80 → **P1**
4. Moderate + LOW 신뢰도 = 40 × 0.3 = 12 → **P3**

**신뢰도 하향 시 설명 예시**:
```
⚠️ 이 치명적(Critical) 이슈는 중간 신뢰도(MEDIUM)로 인해 P1으로 분류되었습니다.
백엔드 코드를 직접 확인하지 못해 런타임 동작을 완전히 검증할 수 없습니다.
```

## 리포트 말미 필수 기재

```
## 검증 투명성

### 검증 통계
- 검증한 가설: N건
- 거부된 가설 (사전 제거): N건
- 보고된 이슈: N건
- 거부율: X%

### 거부 사유 분류

| 사유 | 건수 | 예시 |
|------|------|------|
| 반증됨 | N | "X가 없다" → Grep으로 발견 |
| Self-Challenge 기각 | N | SC-3 라이브러리 오해, SC-5 의도된 패턴 등 |
| 범위 외 | N | 백엔드 이슈이나 백엔드 미제공 |
| 이미 수정됨 | N | 코드 읽어보니 이미 구현됨 |
| 오판 | N | 코드 로직 잘못 이해 |
| 중복 | N | 다른 에이전트가 이미 보고 |
| 신뢰도 불충분 | N | 증거 약함 (LOW 미만) |

**거부 사유 정의**:
- **반증됨**: 3단계 검증에서 주장이 거짓으로 판명 (예: "X가 없다"고 했으나 Grep으로 발견)
- **Self-Challenge 기각**: 3.5단계에서 SC-1~SC-5 중 ✗ 판정 (SC-1 dead code, SC-3 라이브러리 오해, SC-5 의도된 패턴 등)
- **범위 외**: 리뷰 범위를 벗어남 (예: 백엔드 이슈이나 백엔드 코드 미제공)
- **이미 수정됨**: Read로 확인 결과 코드가 이미 수정되어 있음
- **오판**: 코드 로직을 잘못 이해하여 실제로는 이슈가 아님
- **중복**: 다른 에이전트가 이미 동일 이슈 보고
- **신뢰도 불충분**: 증거가 너무 약해 보고 기준(LOW 60%) 미달

**허위 양성 패턴 추적**:
이 분류를 통해 체계적인 허위 양성 원인을 식별하고 개선합니다.
- **반증됨**이 많으면 → 에이전트가 3단계 검증 도구를 제대로 사용하지 않음
- **Self-Challenge 기각**이 많으면 → SC 체크리스트를 강화하거나 에이전트 프롬프트 개선
- **범위 외**가 많으면 → Phase 0B 범위-에이전트 필터링 강화 필요
- **이미 수정됨**이 많으면 → 에이전트가 오래된 코드 정보 참조
- **오판**이 많으면 → 에이전트의 코드 이해 능력 개선 필요
```
