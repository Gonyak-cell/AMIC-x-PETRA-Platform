# Workflow Orchestration Rules

> 이 파일은 Claude Code가 이 프로젝트에서 작업할 때 따라야 할 **메타 워크플로우 원칙**을 정의한다.
> 기존 규칙 파일(`verified-claim-protocol.md`, `review-documentation.md` 등)과 **충돌하지 않으며**, 모든 작업 유형에 공통 적용된다.
> 작성일: 2026-02-23 09:30:11

---

## 1. 플랜 우선 원칙 (Plan Node Default)

- **비자명 작업(3단계 이상 또는 아키텍처 결정 포함)은 반드시 플랜 모드(`EnterPlanMode`)로 진입**한다.
- 작업 도중 막히거나 가정이 틀렸다면 **즉시 멈추고 리플랜**한다. 억지로 밀어붙이지 않는다.
- 플랜은 구현 단계뿐 아니라 **검증 단계도 포함**해 작성한다.
- 모호성을 줄이기 위해 **상세한 스펙을 선행 작성**한다.

**플랜 모드 진입 기준** (하나라도 해당하면 진입):
- 3개 이상의 파일을 수정해야 하는 경우
- 아키텍처/설계 결정이 필요한 경우
- 접근 방법이 2가지 이상 존재하는 경우
- 요구사항이 불명확하거나 사용자 선호가 필요한 경우

**예외** (플랜 없이 바로 실행 가능):
- 오타 수정, 1~2줄 버그 픽스, 단순 리네임

## 2. 서브에이전트 전략 (Subagent Strategy)

**원칙**: 서브에이전트를 적극 활용해 **메인 컨텍스트 윈도우를 보호**한다.

### 에이전트 유형별 사용 지침

| 에이전트 타입 | 용도 | 언제 사용 |
|---|---|---|
| `Explore` | 코드베이스 탐색, 파일 검색, 패턴 파악 | 모르는 영역 탐색, 파일 구조 파악 |
| `Plan` | 구현 방식 설계, 트레이드오프 분석 | 복잡한 기능 설계 |
| `Bash` | 명령 실행, git 작업 | 터미널 작업 |
| `general-purpose` | 복잡한 멀티스텝 리서치 | 광범위한 탐색이 필요할 때 |

### 병렬화 원칙
- **독립적인 탐색 작업은 병렬로 실행**한다 (최대 3개 동시).
- 각 에이전트는 **하나의 명확한 역할**만 수행한다. 범위 확장 금지.
- 에이전트 결과를 기다린 후에만 의존 작업을 진행한다.

### 이 모노레포에서의 영역 분할 예시
```
탐색 에이전트 1: amic-platform/src/ (프론트엔드)
탐색 에이전트 2: fdd/ or kiis/ or im/ (백엔드 모듈)
탐색 에이전트 3: deal-mgmt/ (MA 워크플로우)
```

## 3. 자기 개선 루프 (Self-Improvement Loop)

사용자가 내 작업을 수정하거나 오류를 지적하면:

1. **즉시 MEMORY.md에 학습 내용을 기록**한다.
   - 경로: `C:\Users\서지원\.claude\projects\...\memory\MEMORY.md`
   - 반복될 수 있는 패턴이면 별도 토픽 파일 생성 (`debugging.md`, `patterns.md` 등)
2. **동일 실수를 방지하는 규칙을 작성**하여 관련 `.claude/rules/` 파일에 추가한다.
3. **세션 시작 시 MEMORY.md를 검토**하여 이전 학습 내용을 환기한다.
4. 틀린 것으로 판명된 메모리 항목은 **즉시 삭제하거나 수정**한다.

> ※ 원본 이미지의 `tasks/lessons.md` 역할을 **Claude Code 자동 메모리 시스템(MEMORY.md)** 이 대체한다.

## 4. 완료 검증 기준 (Definition of Done)

**"작동한다고 생각한다"는 완료가 아니다. 작동함을 증명해야 완료다.**

### 공통 기준 (모든 작업)
- [ ] "Staff Engineer가 이 코드를 승인할까?" 자문
- [ ] 변경된 동작과 기존 동작의 차이를 설명할 수 있음
- [ ] 의도치 않은 사이드 이펙트가 없음을 확인

### 작업 유형별 DoD

**Feature (신규 기능)**:
- [ ] 핵심 흐름이 실제로 실행됨 (테스트 또는 수동 확인)
- [ ] TypeScript 타입 오류 없음 (`tsc --noEmit`)
- [ ] ESLint 통과
- [ ] 백엔드 API 연동 시 실제 응답 확인

**Bugfix (버그 수정)**:
- [ ] 원래 버그가 재현되지 않음을 확인
- [ ] 수정 범위가 최소화됨 (필요 이상 변경 없음)
- [ ] 연관된 코드 경로가 깨지지 않음

**Refactor (리팩터링)**:
- [ ] 동작이 변경되지 않음 (기존 테스트 전원 통과)
- [ ] 코드가 실제로 더 단순해졌음 (라인 수, 복잡도)

> ※ 코드 리뷰의 이슈 검증은 별도로 `verified-claim-protocol.md`의 VCP 프로세스를 따른다.

## 5. 우아함 추구 (Demand Elegance)

**비자명 변경 작업 시, 구현 전 "더 우아한 방법이 있는가?"를 자문한다.**

### 적용 기준
- **적용**: 새 기능, 복잡한 로직, 리팩터링, 시스템 설계
- **건너뜀**: 오타 수정, 간단한 버그 픽스, 직관적인 1~2줄 변경

### 자가 검토 질문
1. "더 적은 코드로 같은 결과를 낼 수 있는가?"
2. "기존 유틸리티/패턴을 재사용할 수 있는가?" (→ `Grep`으로 먼저 탐색)
3. "이 접근 방식이 6개월 후에도 이해 가능한가?"
4. "프레임워크나 언어가 이미 제공하는 기능을 직접 구현하려는 건 아닌가?"

**해킹처럼 느껴지는 수정이라면**: "지금 알고 있는 모든 것을 바탕으로, 우아한 해결책을 구현하라."

## 6. 자율 버그 수정 (Autonomous Bug Fixing)

> **⚠ 필수**: `.claude/rules/bugfix-root-cause-verification.md` (RCV 규칙) 적용.
> 원인을 추측하여 수정하지 않는다. 반드시 원인을 **확인하고 확정한 후** 수정한다.

버그 리포트가 주어지면:
1. **즉시 조사를 시작한다. 핸드홀딩을 요청하지 않는다.**
2. 로그, 오류 메시지, 실패한 테스트를 **직접 추적**하여 근본 원인을 파악한다.
3. 사용자 컨텍스트 전환 없이 **자율적으로 해결**한다.
4. CI 실패 테스트는 **별도 지시 없이 자율 수정**한다.

**자율 수정 절차**:
```
1. 오류 메시지/로그 분석 (전문 읽기)
2. Read + Grep/Glob으로 관련 코드 직접 확인
3. 근본 원인 확정 선언 ← 수정의 전제 조건 (RCV 게이트 2)
4. 최소 범위 수정 (확정된 원인의 정확한 위치만)
5. 수정 결과 검증 (DoD 체크)
```

**3단계(원인 확정) 없이 4단계(수정) 진행 금지.**

**자율 수정의 한계** (사용자 확인 필요):
- 스키마 변경, API 계약 변경 등 하위 호환성 영향 있는 수정
- 보안 관련 수정 (인증, 권한)
- 데이터 마이그레이션 포함 수정

## 7. 태스크 관리 (Task Management)

> ※ 원본 이미지의 `tasks/todo.md` 역할은 **Claude Code 내장 `TodoWrite` 도구**가 대체한다.

### 6단계 프로세스
1. **Plan First** — 3단계 이상 작업은 `TodoWrite`로 체크리스트 작성
2. **Verify Plan** — 플랜 모드에서 사용자 승인 후 구현 시작
3. **Track Progress** — 작업 완료 즉시 `TodoWrite`로 상태 업데이트 (`completed`)
4. **Explain Changes** — 자연스러운 마일스톤마다 진행 상황 요약
5. **Document Results** — 수정/오류 내역은 `review/` 폴더에 기록 (`review-documentation.md` 참조)
6. **Capture Lessons** — 사용자 수정 후 MEMORY.md 업데이트

### TodoWrite 사용 기준
- 사용: 3단계 이상, 멀티파일 수정, 복잡한 디버깅
- 사용 안 함: 단일 파일 1~2줄 수정, 단순 조회, 설명만 요청

## 8. 핵심 원칙 (Core Principles)

| 원칙 | 설명 |
|------|------|
| **Simplicity First** | 가능한 가장 단순한 변경. 최소 코드 영향. |
| **No Laziness** | 근본 원인을 찾는다. 임시방편 금지. 시니어 개발자 기준 적용. |
| **Minimal Impact** | 변경은 요청된 것만 건드린다. 의도치 않은 버그 도입 금지. |
| **No Speculation** | 읽지 않은 코드에 대해 제안하지 않는다. 먼저 읽는다. |
| **Reversibility Aware** | 되돌리기 어려운 작업은 사용자 확인 후 진행. |
