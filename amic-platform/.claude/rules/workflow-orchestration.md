# Workflow Orchestration Rules

> 이 파일은 Claude Code가 이 프로젝트에서 작업할 때 따라야 할 **메타 워크플로우 원칙**을 정의한다.

---

## 1. 플랜 우선 원칙 (Plan Node Default)

비자명 작업(3단계 이상 또는 아키텍처 결정 포함)은 반드시 `EnterPlanMode`로 진입한다.
작업 도중 막히거나 가정이 틀렸다면 즉시 멈추고 리플랜한다.
Plan mode 진입 시 `plan-review` 스킬의 4단계 순차 리뷰 원칙을 적용한다.

**진입 기준** (하나라도 해당): 3+파일 수정, 아키텍처 결정, 접근 방법 2+개, 불명확 요구사항.
**예외**: 오타 수정, 1~2줄 버그 픽스, 단순 리네임.

---

## 2. 서브에이전트 전략

서브에이전트를 적극 활용해 **메인 컨텍스트 윈도우를 보호**한다.

- `Explore`: 코드베이스 탐색, 파일/패턴 파악
- `Plan`: 복잡한 기능 설계, 트레이드오프 분석
- `general-purpose`: 광범위 멀티스텝 리서치
- **독립 작업은 병렬 실행** (최대 3개). 각 에이전트는 하나의 역할만 수행.

---

## 3. 자기 개선 루프

사용자가 오류를 지적하면:
1. 즉시 `MEMORY.md`에 학습 내용 기록
2. 반복 패턴이면 `.claude/rules/` 규칙 추가
3. 틀린 메모리 항목은 즉시 삭제/수정

---

## 4. 완료 검증 기준 (Definition of Done)

**"작동한다고 생각한다"는 완료가 아니다. 작동함을 증명해야 완료다.**

| 작업 유형 | 필수 검증 |
|----------|---------|
| **Feature** | 핵심 흐름 실행 확인 + `tsc --noEmit` + ESLint + API 응답 확인 |
| **Bugfix** | 버그 재현 불가 확인 + 수정 범위 최소화 + 연관 경로 무결 |
| **Refactor** | 기존 테스트 전원 통과 + 실제로 단순해졌음 증명 |

공통: "Staff Engineer가 승인할 코드인가?" 자문.

---

## 5. 우아함 추구

비자명 변경 시 구현 전 자문: "더 적은 코드로 같은 결과?", "기존 유틸 재사용 가능?", "6개월 후 이해 가능?", "프레임워크 제공 기능을 직접 구현하려는 건 아닌가?"

**적용**: 새 기능, 복잡한 로직, 리팩터링. **건너뜀**: 오타, 간단한 버그 픽스.

---

## 6. 자율 버그 수정

> **필수**: `.claude/rules/bugfix-root-cause-verification.md` (RCV 규칙) 적용.

버그 리포트 시 즉시 조사 시작. 핸드홀딩 요청하지 않는다.

**절차**: 오류 분석 → Read/Grep 확인 → **근본 원인 확정 선언** → 최소 범위 수정 → DoD 체크.
3단계(원인 확정) 없이 4단계(수정) 진행 금지.

**사용자 확인 필요**: 스키마/API 계약 변경, 보안 수정, 데이터 마이그레이션.

---

## 7. 태스크 관리

3단계 이상 작업은 `TodoWrite`로 체크리스트 작성 → 사용자 승인 → 완료 즉시 상태 업데이트.
마일스톤마다 진행 요약. 사용자 수정 후 MEMORY.md 업데이트.

---

## 7-1. 우선순위 전환 시 백로그 보존

> **핵심**: 새 작업으로 전환할 때, 기존 미완료 작업을 잊지 않는다.

**적용 시점**: 사용자가 진행 중인 작업과 다른 새 작업을 지시할 때 자동 적용.

1. **전환 감지**: 현재 작업과 새 지시가 다른 기능/모듈이면 "우선순위 전환"으로 판단
2. **백로그 기록**: `CLAUDE.local.md`의 Session Progress에 중단된 작업을 기록 (작업명 + 보류 사유 + 관련 파일 경로)
3. **사용자 확인**: "기존 [X] 작업을 보류하고 [Y]로 전환합니다. 맞습니까?" 확인

**위반 감지 신호**: 새 기능 지시를 받고 기존 작업을 기록 없이 전환하려 함.

---

## 7-2. 모호한 지시 확인

> **핵심**: 해석이 여러 가지 가능한 지시는 구현 전에 반드시 확인한다.

**적용 시점**: 구현 지시를 받았으나 구체적 동작이 불명확할 때 자동 적용.

| 지시 패턴 | 확인 질문 예시 |
|----------|-------------|
| UI 용어 모호 ("접히기", "토글", "축소") | "어떤 범위? 전체 사이드바 축소 vs 섹션 접기" |
| 기능 이름만 ("챗봇 구현", "검색 추가") | "어떤 데이터 소스? 어떤 UI 형태?" |
| 범위 불명확 ("전부", "다", "모든") | "구체적으로 어떤 항목들?" |

**확인 없이 진행 가능**: 파일 경로+라인번호 명시된 수정, 스크린샷/에러 로그 동반 버그 리포트, 이전 합의된 스펙의 후속 구현.

---

## 7-3. 아키텍처 지시의 명시적 종결

> **핵심**: 아키텍처 레벨 탐색 지시는 결론을 명시적으로 보고한다.

**적용 시점**: "벤치마킹", "분석", "검토", "활용 방안" 등 탐색적 지시를 받았을 때.

탐색 완료 후 반드시 다음 중 하나를 보고:
1. **즉시 구현 가능** → 구현 계획 제시
2. **추가 설계 필요** → 필요한 결정 사항 목록 + `CLAUDE.local.md`에 기록
3. **현재 인프라로 구현 불가** → 사유 설명 + 대안 제시

**절대 금지**: 탐색 결과를 보고하지 않고 다음 작업으로 넘어가는 것.

---

## 8. 핵심 원칙

| 원칙 | 설명 |
|------|------|
| **Simplicity First** | 가능한 가장 단순한 변경. 최소 코드 영향. |
| **No Laziness** | 근본 원인을 찾는다. 임시방편 금지. 시니어 개발자 기준. |
| **Minimal Impact** | 요청된 것만 건드린다. 의도치 않은 버그 도입 금지. |
| **No Speculation** | 읽지 않은 코드에 대해 제안하지 않는다. 먼저 읽는다. |
| **Reversibility Aware** | 되돌리기 어려운 작업은 사용자 확인 후 진행. |
