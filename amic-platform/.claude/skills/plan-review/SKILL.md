# Plan Mode 리뷰 원칙

> **핵심**: 코드 변경 계획 수립 전 철저히 리뷰. 모든 이슈에 트레이드오프를 설명하고 권장 사항을 제시하며 사용자 의견을 묻는다.

## 적용 시점

Plan mode 진입 시 **자동 적용**: 코드 변경을 수반하는 모든 계획 수립 작업 (새 기능, 리팩토링, 버그 수정, 아키텍처 변경).

## 엔지니어링 선호도

| 원칙 | 설명 |
|------|------|
| **DRY** | 코드 중복은 즉시 이슈로 보고 |
| **테스트 타협 불가** | 부족보다 과잉이 낫다 |
| **충분한 엔지니어링** | 과소(hacky) ✕, 과잉(성급한 추상화) ✕ |
| **Edge cases 철저** | 더 많이 처리 > 덜 처리 |
| **명시적 > 기교** | explicit 코드 지향 |

## Step 0: 리뷰 규모 선택

계획 수립 **전** `AskUserQuestion`:
- **옵션 1 — 큰 변경**: 섹션별 최대 4개 이슈
- **옵션 2 — 작은 변경**: 섹션별 1개 질문

## Step 1~4: 4단계 순차 리뷰

### 섹션 1: 아키텍처
시스템 설계, 의존성 그래프, 데이터 흐름, 확장성, 보안 아키텍처

### 섹션 2: 코드 품질
모듈 구조, **DRY 위반**, 에러 처리, 기술 부채, 과잉/과소 엔지니어링

### 섹션 3: 테스트
커버리지 공백, 테스트 품질, **누락 edge case**, 실패 모드

### 섹션 4: 성능
N+1 쿼리, 메모리, 캐싱 기회, 느린 코드 경로

## 각 섹션 완료 후

**반드시** `AskUserQuestion`으로 피드백 요청 후 다음 섹션 진행.

## 이슈 보고 형식

```
### 이슈 {번호}: {제목}
**위치**: `파일명:줄번호`
**문제**: [설명]

| 옵션 | 설명 | 구현 노력 | 위험 | 영향 범위 | 유지보수 부담 |
|------|------|----------|------|----------|-------------|
| **A (권장)** | [이유] | ... | ... | ... | ... |
| B | [대안] | ... | ... | ... | ... |
| C | 아무것도 하지 않음 | 없음 | [방치 위험] | — | — |
```

## 절대 금지

- 사용자 확인 없이 방향/우선순위 가정
- 트레이드오프 없는 권장 사항
- 리뷰 섹션 건너뛰기
- `AskUserQuestion` 없이 다음 섹션 진행
