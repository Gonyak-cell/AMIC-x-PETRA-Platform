# Systematic Debugging

> 출처: [obra/superpowers](https://github.com/obra/superpowers) — 프로젝트에 맞게 적용

## 핵심 원칙

```
근본 원인 조사 없이 수정 금지
```

Phase 1을 완료하지 않으면 수정을 제안할 수 없다.

## 사용 시점

모든 기술적 이슈에 사용:
- 테스트 실패
- 프로덕션 버그
- 예상치 못한 동작
- 성능 문제
- 빌드 실패
- 통합 이슈

**특히 다음 상황에서 반드시 사용:**
- 시간 압박 (급할수록 추측하고 싶어짐)
- "간단한 수정" 하나면 될 것 같을 때
- 이미 여러 수정을 시도했을 때
- 이전 수정이 작동하지 않았을 때

## 4단계 프로세스

### Phase 1: 근본 원인 조사

**수정을 시도하기 전에:**

1. **에러 메시지를 꼼꼼히 읽기**
   - 에러, 경고를 건너뛰지 않기
   - 스택 트레이스 전체 읽기
   - 라인 번호, 파일 경로, 에러 코드 기록

2. **일관되게 재현**
   - 안정적으로 트리거할 수 있는가?
   - 정확한 재현 단계는?
   - 재현 불가 → 더 많은 데이터 수집, 추측 금지

3. **최근 변경 확인**
   - 이 문제를 일으킬 수 있는 변경은?
   - `git diff`, 최근 커밋, 의존성/설정 변경

4. **멀티 컴포넌트 시스템에서 증거 수집**

   모노레포 구조 (FDD ↔ KIIS ↔ IM ↔ deal-mgmt ↔ 프론트엔드):
   ```
   각 컴포넌트 경계마다:
     - 컴포넌트에 들어가는 데이터 로깅
     - 컴포넌트에서 나오는 데이터 로깅
     - 환경/설정 전파 검증
     - 각 레이어의 상태 확인
   ```

5. **데이터 흐름 추적**
   - 잘못된 값의 출발점은 어디?
   - 누가 이 잘못된 값으로 호출했는가?
   - 소스를 찾을 때까지 역추적
   - 증상이 아닌 소스에서 수정

### Phase 2: 패턴 분석

1. **동작하는 예제 찾기** — 같은 코드베이스에서 유사한 동작 코드 찾기
2. **참조와 비교** — 참조 구현을 완전히 읽기 (훑어보기 금지)
3. **차이점 식별** — 동작하는 것과 깨진 것의 모든 차이점 목록화
4. **의존성 이해** — 필요한 컴포넌트, 설정, 환경, 가정

### Phase 3: 가설과 테스트

1. **단일 가설 수립** — "X가 근본 원인이다, 왜냐하면 Y" 명확히 기술
2. **최소 테스트** — 가장 작은 변경으로 가설 테스트. 한 번에 하나의 변수만.
3. **계속하기 전에 검증** — 성공 → Phase 4. 실패 → 새 가설.
4. **모를 때** — "X를 모르겠다"고 말하기. 모르는 척 금지.

### Phase 4: 구현

1. **실패하는 테스트 케이스 작성** — 수정 전 반드시
2. **단일 수정 구현** — 근본 원인 해결. 한 번에 하나. "하는 김에" 개선 금지.
3. **수정 검증** — 테스트 통과? 다른 테스트 깨지지 않았는가?
4. **수정 실패 시** — 3회 이상 실패하면 아키텍처 재검토. 더 이상의 수정 시도 전에 사용자와 논의.

## 위험 신호 — 멈추고 프로세스 따르기

다음을 생각하고 있다면 STOP:
- "지금은 임시로, 나중에 조사"
- "X를 바꿔보고 되는지 보자"
- "여러 변경을 한 번에 넣고 테스트"
- "아마 X일 거야, 수정하자"
- "완전히 이해 못 하지만 이게 될 수도"

## 빠른 참조

| Phase | 핵심 활동 | 성공 기준 |
|-------|----------|----------|
| 1. 근본 원인 | 에러 읽기, 재현, 변경 확인, 증거 수집 | 무엇이 왜인지 이해 |
| 2. 패턴 | 동작 예제 찾기, 비교 | 차이점 식별 |
| 3. 가설 | 이론 수립, 최소 테스트 | 확인 또는 새 가설 |
| 4. 구현 | 테스트 작성, 수정, 검증 | 버그 해결, 테스트 통과 |
