# Plan Mode 리뷰 원칙 (Plan Mode Review Standards)

> **핵심**: 코드 변경 계획을 세우기 전에 철저히 리뷰한다. 모든 이슈에 구체적 트레이드오프를 설명하고, 주관이 뚜렷한 권장 사항을 제시하며, 방향을 가정하기 전에 사용자 의견을 묻는다.

## 적용 시점

Plan mode 진입 시 **자동 적용**:
- 코드 변경을 수반하는 모든 계획 수립 작업
- 새 기능 구현, 리팩토링, 버그 수정 계획, 아키텍처 변경

## 엔지니어링 선호도 (권장 사항의 기준)

이 선호도를 지침으로 삼아 모든 권장 사항을 제시한다:

| 원칙 | 설명 |
|------|------|
| **DRY** | 반복을 **공격적으로** 지적한다. 코드 중복은 즉시 이슈로 보고 |
| **테스트 타협 불가** | 잘 테스트된 코드는 비협상 사항. 부족보다 과잉이 낫다 |
| **충분한 엔지니어링** | 과소(취약, hacky/땜질식) ✕, 과잉(성급한 추상화, 불필요한 복잡성) ✕ |
| **Edge cases 철저** | 덜 처리하기보다 더 많이 처리한다. 신중함 > 속도 |
| **명시적 > 기교** | explicit 코드를 지향한다. clever 코드는 지양 |

## 필수 절차

### Step 0: 리뷰 규모 선택

계획 수립을 시작하기 **전에** 반드시 `AskUserQuestion`으로 물어본다:

- **옵션 1 — 큰 변경**: 대화형으로 한 번에 한 섹션씩 진행 (아키텍처 → 코드 품질 → 테스트 → 성능). 각 섹션에서 **최대 4개** 주요 이슈.
- **옵션 2 — 작은 변경**: 대화형으로 진행하되 리뷰 섹션당 **1개** 질문만.

### Step 1~4: 4단계 순차 리뷰

각 섹션을 **순서대로** 진행하며, 한 섹션이 끝나야 다음으로 넘어간다.

#### 섹션 1: 아키텍처 리뷰
- 전반적인 시스템 설계 및 컴포넌트 경계
- 의존성 그래프 및 결합도 문제
- 데이터 흐름 패턴 및 잠재적 병목 지점
- 확장성 특성 및 단일 장애점(single points of failure)
- 보안 아키텍처 (인증, 데이터 접근, API 경계)

#### 섹션 2: 코드 품질 리뷰
- 코드 구성 및 모듈 구조
- **DRY 위반 사항** — 공격적으로 지적
- 에러 처리 패턴 및 누락된 edge cases (명시적으로 언급)
- 기술 부채 핫스팟
- 엔지니어링 선호도에 비추어 과잉/과소 엔지니어링된 영역

#### 섹션 3: 테스트 리뷰
- 테스트 커버리지 공백 (단위, 통합, e2e)
- 테스트 품질 및 단언문(assertion)의 강도
- **누락된 edge case 커버리지** — 철저히 할 것
- 테스트되지 않은 실패 모드 및 에러 경로

#### 섹션 4: 성능 리뷰
- N+1 쿼리 및 데이터베이스 접근 패턴
- 메모리 사용 문제
- 캐싱 기회
- 느리거나 복잡도가 높은 코드 경로

### Step 5: 각 섹션 완료 후

각 섹션이 끝나면 **반드시** `AskUserQuestion`으로 피드백을 요청한 후 다음 섹션으로 넘어간다.

## 이슈 보고 형식 (필수)

발견한 **모든** 이슈(버그, 코드 스멜, 설계 우려, 위험)에 대해:

### 형식

```
### 이슈 {번호}: {제목}

**위치**: `파일명:줄번호`
**문제**: [구체적 설명]

| 옵션 | 설명 | 구현 노력 | 위험 | 영향 범위 | 유지보수 부담 |
|------|------|----------|------|----------|-------------|
| **A (권장)** | [권장 옵션 설명 + 이유] | ... | ... | ... | ... |
| B | [대안 설명] | ... | ... | ... | ... |
| C | 아무것도 하지 않음 | 없음 | [방치 위험] | — | — |
```

### 규칙

- 이슈에는 **번호**를 매긴다 (1, 2, 3...)
- 옵션에는 **문자**를 부여한다 (A, B, C)
- **권장 옵션은 항상 A (첫 번째)**
- 타당한 경우 "아무것도 하지 않음" 옵션 포함
- 각 옵션: **구현 노력, 위험, 영향, 유지보수 부담** 4가지 필수 명시
- 권장 이유는 위의 **엔지니어링 선호도**에 맞춰 설명

## 절대 금지

- 사용자 확인 없이 방향/우선순위 가정
- 트레이드오프 없는 권장 사항 제시
- 리뷰 섹션 건너뛰기 (해당 없으면 "해당 이슈 없음" 명시)
- 사용자 일정이나 규모 우선순위를 임의로 가정
- `AskUserQuestion` 없이 다음 섹션으로 진행

## 위반 감지 신호

다음을 쓰거나 생각하려 한다면 **STOP — 이 규칙으로 돌아가기**:
- "이건 큰 문제가 아니므로 넘어가자"
- "사용자는 아마 이 방향을 선호할 것이다"
- "시간이 없을 테니 간단히 하자"
- 트레이드오프 테이블 없이 "~하면 됩니다" 단정
