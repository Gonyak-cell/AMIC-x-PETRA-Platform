# 코드 리뷰 체크리스트 (Code Review Checklist)

> **작성일**: 2026-02-27 13:33:00

## §0 변경 범위 파악

리뷰 시작 전 반드시 수행:

1. `git diff` + `git diff --cached`로 실제 변경 내역 확인
2. 변경된 파일 전체를 `Read`로 읽기 (변경된 줄만이 아닌 파일 전체)
3. 변경 파일이 import/호출하는 모듈과 의존 타입도 `Read`
4. 최초 계획 문서가 있으면 `Read`로 읽어서 계획된 기능 목록 파악
5. 동일 모듈의 유사 파일을 1~2개 `Read` (패턴 비교 기준 확보)

## §1 정합성 — Consistency

변경된 코드가 기존 코드베이스의 패턴, 컨벤션, 구조와 일치하는지 검증.

### [백엔드]

1. **계층 구조**: 라우터→서비스→모델 3계층 분리 준수 (라우터에 비즈니스 로직 혼입 금지)
2. **네이밍 컨벤션**: 함수명 snake_case, 클래스명 PascalCase, 테이블명 snake_case 복수형
3. **import 순서**: stdlib → third-party → local 순서 유지
4. **스키마 패턴**: Pydantic v2 `model_config = ConfigDict(from_attributes=True)`, `Create`/`Update`/`Response` 분리
5. **에러 처리**: 기존 커스텀 예외 클래스(`AppError`, `NotFoundError` 등) 활용, 무분별 새 예외 생성 여부
6. **로깅**: `logging.getLogger(__name__)` 사용, 구조화된 JSON 로깅 일관성
7. **의존성 주입**: `Depends()` 패턴 일관성, `get_current_user` 주입 방식 동일
8. **동일 모듈 유사 코드 비교**: 같은 디렉토리의 다른 파일을 `Read`로 읽어서 패턴 비교
9. **SQLAlchemy 크로스 DB 호환성**: `JSON().with_variant(JSONB, "postgresql")` + `Uuid` 사용 (`ci-regression-prevention.md` Guard 2). PostgreSQL 전용 타입(`mapped_column(JSONB`, `mapped_column(UUID(as_uuid`) 직접 사용 금지
10. **Alembic 마이그레이션 패턴**: `downgrade()` 반드시 구현, hatchling 빌드 백엔드 + `packages = ["app"]` 명시 (`ci-regression-prevention.md` Guard 6)
11. **pyproject.toml dev 의존성**: `[project.optional-dependencies]` 사용 (pip 호환). `[dependency-groups]`(PEP 735) 사용 금지 (`ci-regression-prevention.md` Guard 7)

### [프론트엔드]

1. **훅 패턴**: `useQuery`/`useMutation` 사용 방식이 기존 훅들과 동일한지
2. **컴포넌트 패턴**: Props 인터페이스 정의, `forwardRef` 사용, `cn()` 유틸리티 사용
3. **파일 구조**: `modules/{module}/pages/`, `hooks/`, `types/`, `components/` 구조 준수
4. **타입 정의 위치**: 모듈별 `types/` 폴더에 정의, 공유 타입은 `src/types/`
5. **API 호출 패턴**: axios 인스턴스 사용, `withCredentials: true`, 에러 핸들링 일관성
6. **동일 모듈 유사 페이지 비교**: 같은 모듈의 다른 페이지를 `Read`로 읽어서 구조 비교
7. **GSAP 애니메이션 패턴**: `useGSAP` 훅 사용, cleanup 패턴, ScrollTrigger 일관성

## §2 완전성 — Completeness

변경된 코드가 의도한 기능을 완전히 구현했는지 검증.

### [기능 완전성]

1. **최초 계획 대비 누락 검증**: 계획 문서의 각 항목에 대해 ✅/❌/⚠️ 체크리스트 작성
2. **엔드포인트 완전성**: CRUD 중 누락된 메서드가 없는지
3. **에러 경로**: 정상 경로만 구현하고 에러/예외 경로 처리를 빠뜨리지 않았는지
4. **엣지 케이스**: 빈 목록, null 값, 권한 없는 사용자, 존재하지 않는 리소스 등 경계 상황 처리
5. **유효성 검증**: 입력 데이터에 대한 검증이 충분한지 (필수 필드, 형식, 범위)

### [통합 완전성]

1. **라우터 등록**: 새 라우터가 `main.py`에 `include_router()`로 등록되었는지
2. **프론트엔드 라우팅**: 새 페이지가 `App.tsx` 또는 모듈별 `Routes.tsx`에 등록되었는지
3. **사이드바/내비게이션**: 새 페이지에 대한 메뉴 항목이 추가되었는지
4. **타입 export**: 새 타입이 `index.ts` 배럴 파일에서 export되는지
5. **마이그레이션**: DB 스키마 변경 시 Alembic 마이그레이션 파일 존재, `downgrade()` 구현
6. **Docker 통합**: 새 서비스 추가 시 `docker-compose.yml`, `Dockerfile` 업데이트 여부
7. **환경변수 동기화**: 새 환경변수 추가 시 `.env.example`, `config.py`/`settings.py` 동기화 여부

### [테스트 완전성]

1. **새 기능 대응 테스트 존재 여부**: 추가된 API 엔드포인트, 새 컴포넌트에 대한 테스트
2. **기존 테스트 영향**: 변경으로 인해 기존 테스트가 깨질 수 있는지 분석
3. **테스트 품질**: 실제 동작을 검증하는지 (구현 세부가 아닌 행동 테스트)

## §3 품질 — Quality & Depth

코드의 기술적 품질과 엔지니어링 수준을 평가.

### [설계 품질]

1. **적절한 추상화 수준**: 과도한 추상화(불필요한 헬퍼/유틸리티) 또는 부족한 추상화(중복 코드) 여부
2. **관심사 분리**: 한 함수/클래스가 너무 많은 책임을 지지 않는지 (SRP)
3. **데이터 흐름 명확성**: 데이터가 어디서 오고 어디로 가는지 코드만 보고 추적 가능한지
4. **상태 관리**: 불필요한 상태 사용 여부, 파생 가능한 값을 별도 상태로 관리하지 않는지

### [구현 수준]

1. **타입 시스템 활용도**: 제네릭, 유니온, 디스크리미네이티드 유니온 등 TypeScript 기능 적절 활용 / Python 타입 힌트 완비
2. **비동기 처리**: async/await 올바른 사용, 불필요한 await 없는지, 병렬 가능한 작업의 동시 실행 여부
3. **쿼리 최적화**: N+1 방지, 적절한 인덱싱, 불필요한 전체 조회 여부
4. **메모리/성능**: 대용량 데이터 페이지네이션, 불필요한 전체 로딩 방지, 프론트엔드 불필요 리렌더링 방지

### [코드 가독성]

1. **함수/변수 네이밍**: 의미가 명확한지, 약어 남용 여부
2. **함수 길이**: 한 함수가 50줄을 넘지 않는지 (넘으면 분리 권장)
3. **주석 필요성**: 복잡한 비즈니스 로직에 대한 설명 주석이 있는지 (자명한 코드에 불필요한 주석이 없는지)

## §4 안정성 — Stability & Safety

프로덕션 환경에서 안정적으로 동작할 수 있는지 검증.

### [보안]

> 상세 체크리스트: `amic-platform/.claude/rules/security-checklist.md` 참조

1. **하드코딩된 시크릿**: API 키, 비밀번호, 토큰이 코드에 포함되어 있지 않은지
2. **인증/인가**: 모든 보호 엔드포인트에 `Depends(get_current_user)` 존재, 권한 체크 누락 여부
3. **입력 검증**: 사용자 입력이 Pydantic 또는 명시적 검증을 거치는지
4. **SQL 인젝션**: 문자열 결합 대신 파라미터화된 쿼리 사용
5. **XSS**: `dangerouslySetInnerHTML` 사용 시 sanitize 여부
6. **CORS**: 와일드카드(`*`) 미사용 확인

### [에러 복원력]

1. **예외 처리 범위**: try-catch/except 블록이 적절한 범위 (너무 넓거나 좁지 않은지)
2. **DB 트랜잭션 롤백**: 예외 발생 시 롤백 보장
3. **외부 서비스 장애 대응**: 다른 백엔드 모듈 호출 실패 시 적절한 폴백/에러 반환
4. **타임아웃**: 외부 API/DB 호출에 적절한 타임아웃 설정

### [데이터 무결성]

1. **DB 제약 조건**: NOT NULL, UNIQUE, FK 등 적절한 제약 조건 설정
2. **동시성**: 레이스 컨디션 가능성 (동시 업데이트, 중복 생성 등)
3. **마이그레이션 안전성**: 마이그레이션이 기존 데이터를 손상시키지 않는지, 대용량 테이블 영향

### [모듈 간 계약]

1. **BE Pydantic ↔ FE TypeScript 필드 일치**: 필드명, 타입, nullable 모두 일치하는지 (실제 양쪽 파일을 Read로 비교)
2. **엔드포인트 경로/메서드 일치**: 프론트엔드 API 호출 URL이 백엔드 라우터 경로와 정확히 매칭
3. **Enum 값 동기화**: 백엔드 Enum 값과 프론트엔드 상수/타입 일치
4. **CORS 형식 일관성**: FDD=str(쉼표 구분), KIIS/IM/MA=list[str](JSON 배열) — `production-error-diagnostic.md` 참조
5. **JWT Secret 일관성**: 4개 API 모듈(FDD/KIIS/IM/MA)의 JWT_SECRET 동일 여부
6. **헬스체크 DB ping**: `health_check` 엔드포인트에 DB 연결 확인이 포함되어 있는지

## §5 허위 리뷰 방지

> **VCP 위임**: 모든 이슈 보고 전 `amic-platform/.claude/rules/verified-claim-protocol.md`의 3.5단계 Self-Challenge(SC-1~SC-6) 적용 필수.

체크리스트 레벨 핵심 원칙:

- **추측 금지**: "아마 ~일 것이다"로 시작하는 이슈 금지. 모든 주장은 실제 Read/Grep 확인 기반
- **증거 첨부 필수**: Read 출력에서 가져온 실제 코드 스니펫을 근거로 제시. 기억이나 재구성 코드 사용 금지
- **파일 전체 맥락**: 변경된 줄만 보지 않고, 파일 전체와 관련 파일을 읽어서 맥락 파악
- **비교 기반 정합성**: 기존 코드베이스의 유사 파일을 반드시 읽어서 패턴 일치 여부 비교 검증

## §6 최초 계획 대비 누락 분석

최초 계획 문서가 제공된 경우 반드시 수행:

1. 계획 문서를 `Read`로 읽고, 명시된 기능/요구사항을 **전수 목록**으로 추출
2. 각 항목에 대해 실제 코드에서 구현 여부를 확인하고 체크리스트 작성:

```
## 최초 계획 대비 구현 검증

| # | 계획된 항목 | 구현 상태 | 검증 근거 (파일:라인) |
|---|-----------|---------|---------------------|
| 1 | {항목1}   | ✅/❌/⚠️ | {파일:라인 또는 미발견} |
| 2 | {항목2}   | ✅/❌/⚠️ | {파일:라인 또는 미발견} |
```

- ✅ 완전 구현: 계획대로 구현 확인됨
- ⚠️ 부분 구현: 일부만 구현 또는 계획과 다르게 구현 (차이점 설명)
- ❌ 누락: 구현되지 않음 (누락 사유 분석)

## §7 품질 게이트 연계

리뷰 시작 시 CI/품질 게이트 결과를 참조하여 중복 검사를 방지하고 효율화한다.

### 실행 방법

CI 결과 조회 가능 시 `gh run list --limit 1` 또는 `gh run view` 실행.
조회 불가하거나 미실행 시 이 섹션을 "CI 결과 미확인" 으로 표시하고 전체 수동 검토.

### 품질 게이트 ↔ 리뷰 항목 매핑

| 품질 게이트 | 통과 시 리뷰 영향 | 실패/미실행 시 |
|------------|------------------|--------------|
| ruff check / eslint | §1 린트 관련 이슈 보고 불필요 `[자동 검증됨]` | §1 린트 준수 수동 검토 |
| pytest / vitest | §2 테스트 존재 여부 자동 확인 `[자동 검증됨]` | §2 테스트 완전성 수동 검토 |
| tsc --noEmit / pyright | §3 타입 에러 없음 `[자동 검증됨]` | §3 타입 활용도 수동 검토 |
| vite build | §2 빌드 성공 `[자동 검증됨]` | §2 통합 완전성 수동 검토 |
| gitleaks | §4 시크릿 스캔 통과 `[자동 검증됨]` | §4 하드코딩 시크릿 수동 검토 |
| Semgrep SAST | §4 SAST 결과 참조 (advisory) | §4 보안 전체 수동 검토 |
| Trivy dependency | §4 의존성 취약점 참조 (advisory) | §4 의존성 수동 검토 |

### 원칙

- **중복 검사 방지**: CI가 이미 잡는 기계적 검사(린트, 타입, 포맷)는 리뷰에서 제외
- **보완 관계**: CI = 기계적 검사, 코드 리뷰 = 논리적 검사 (설계, 정합성, 완전성, 모듈 간 계약)
- **결과 교차 참조**: CI 실패 항목이 있으면 해당 §에서 심층 분석

## §8 출력 형식

### 리뷰 요약

```
## 리뷰 요약
- 총 이슈: N개 (Critical: X, Major: Y, Moderate: Z, Minor: W)
- 계획 대비 구현율: X/Y 항목 (Z%) — §6 결과
- 품질 게이트: N/M 자동 검증됨 — §7 결과
- 전체 평가: {한 줄 요약}
```

### 이슈 형식

> VCP 표준 출력 형식 채택: `amic-platform/.claude/rules/verified-claim-protocol.md` 참조

각 이슈:
```
### [{심각도}] {이슈 제목}
- **위치**: `파일경로:라인번호`
- **카테고리**: 정합성(§1) / 완전성(§2) / 품질(§3) / 안정성(§4)
- **신뢰도**: HIGH / MEDIUM / LOW
- **셀프 체크**: VCP SC-1~SC-6 결과
- **근거**: (실제 Read로 읽은 코드 스니펫)
- **설명**: 무엇이 문제인지
- **영향**: 문제가 발생하면 어떤 일이 일어나는지
- **수정 제안**: 구체적인 코드 변경 방향
```

## §9 반복 리뷰 전략 (2차 이후 리뷰)

> **핵심**: 동일 변경 내역에 대한 2번째 이후 리뷰 요청 시, §0~§8 전체 반복 대신 아래 3가지 전략을 적용한다.
> 전체 반복은 커버리지를 증가시키지 않는다. 관점 전환, 수정 검증, 심층 분석이 효과적이다.

### 적용 조건

- 동일 `git diff` 범위에 대해 이미 1회 이상 리뷰가 수행됨
- 사용자가 "다시 리뷰", "재리뷰", "한번 더 봐줘" 등 반복 리뷰를 요청
- 이전 리뷰의 수정 후 검증을 요청

### 전략 1: 관점 전환 리뷰 (Perspective Shift)

이전 리뷰와 **다른 관점**에서 동일 코드를 검사하여 커버리지를 넓힌다.

| 리뷰 회차 | 기본 관점 | 전환 가능 관점 |
|----------|---------|-------------|
| 1차 (§0~§8) | 전체 체크리스트 | — |
| 2차 | 보안 관점 | §4 [보안] + OWASP Top 10 심층, 인증 흐름 전체 추적, 입력 검증 누락 탐색 |
| 3차 | 성능 관점 | §3 [구현 수준] 심층, DB 쿼리 플랜 분석, 프론트엔드 렌더링 최적화, 번들 크기 영향 |
| 4차 | 에러 처리 관점 | §4 [에러 복원력] 심층, 모든 실패 경로 추적, 외부 서비스 장애 시나리오, 데이터 불일치 상황 |

**실행 방법**:
1. 이전 리뷰에서 사용한 관점을 확인 (리뷰 요약의 카테고리 분포 참조)
2. 이전에 적게 다룬 관점을 선택
3. 해당 관점의 체크 항목을 **심층 수준**으로 확대 (표면 검사 → 코드 흐름 추적)
4. 이전 리뷰에서 발견된 이슈와 동일 패턴이 다른 위치에 있는지 검색 (`Grep`)

**관점별 심층 검사 예시**:
- **보안 관점**: 모든 API 엔드포인트의 인증 데코레이터 유무 `Grep`으로 전수 검사, SQL 쿼리 문자열 결합 패턴 전수 검색
- **성능 관점**: N+1 쿼리 패턴 탐지 (루프 내 DB 호출), 프론트엔드 `useMemo`/`useCallback` 필요성 분석
- **에러 처리 관점**: 모든 `try`/`except` 블록의 catch 범위 분석, 외부 HTTP 호출의 타임아웃/재시도 설정 확인

### 전략 2: 수정 후 재리뷰 (Post-Fix Verification)

이전 리뷰 이슈를 수정한 후 요청된 리뷰. 수정이 올바른지 + **새 이슈를 도입하지 않았는지** 검증.

**실행 절차**:
1. **이전 리뷰 이슈 목록 확인**: 이전 리뷰 리포트를 `Read`
2. **수정 검증**: 각 이슈에 대해 수정된 코드를 `Read`로 확인
   - ✅ 올바르게 수정됨
   - ⚠️ 부분 수정 (일부 누락 또는 다른 방식으로 수정)
   - ❌ 미수정 (변경 없음)
   - 🔄 수정했으나 새 이슈 도입 (regression)
3. **회귀 분석**: 수정된 코드가 다른 기능에 영향을 미치지 않는지 확인
   - 수정 파일의 import/호출 관계를 추적하여 영향 범위 파악
   - 관련 테스트가 여전히 통과하는지 확인
4. **수정 diff 집중 리뷰**: `git diff` 중 이전 리뷰 이후 추가된 변경만 집중 검사

**출력 형식**:
```
## 수정 검증 결과

| # | 이전 이슈 | 수정 상태 | 검증 |
|---|---------|---------|------|
| 1 | [Major] {제목} | ✅ 수정됨 | {파일:라인} 확인 |
| 2 | [Moderate] {제목} | 🔄 새 이슈 도입 | {설명} |
| 3 | [Minor] {제목} | ❌ 미수정 | — |

### 새로 도입된 이슈 (Regression)
{수정으로 인해 새로 발생한 이슈 목록 — VCP 형식}
```

### 전략 3: 범위 축소 심층 리뷰 (Focused Deep Dive)

전체 반복 대신 **고위험 모듈/파일만** 깊게 분석.

**대상 선정 기준** (우선순위 순):
1. 이전 리뷰에서 Critical/Major 이슈가 발견된 파일
2. 변경량이 가장 큰 파일 (git diff --stat 기준)
3. 비즈니스 크리티컬 경로 (인증, 결제, 데이터 변경)
4. 모듈 간 경계 파일 (API 호출, 타입 정의, 라우터)

**심층 분석 방법**:
1. 대상 파일의 **전체 코드**를 처음부터 끝까지 `Read`
2. 호출 체인 추적: 이 함수를 호출하는 곳 + 이 함수가 호출하는 곳 모두 `Grep`/`Read`
3. 데이터 흐름: 입력 → 가공 → 저장 → 반환 전체 경로 추적
4. 실패 시나리오: 각 단계에서 실패하면 어떤 일이 일어나는지 분석
5. 동시성: 같은 리소스에 동시 접근 가능한 코드 경로 있는지 확인

|------|---------|
